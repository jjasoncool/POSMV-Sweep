# com0com 2.2.2.0 在 Windows 11 24H2 可載入並通過自測（2026-10-01）

接續 [2026-10-01-com0com-secure-boot.md](2026-10-01-com0com-secure-boot.md)。環境相同：Windows 11 24H2 build 26100.8875，Secure Boot 開啟，易受攻擊驅動封鎖清單開啟，記憶體完整性未執行。

## 3.0.0.0 被擋的原因

3.0.0.0 的 `com0com.cat` 簽章鏈：CyberCircuits → COMODO RSA Code Signing CA → COMODO RSA Certification Authority → AddTrust External CA Root → Microsoft Code Verification Root（交叉簽章）。CyberCircuits 憑證在 2016-01-04 簽發。Windows 10 1607 起，Secure Boot 開啟時，交叉簽章的核心驅動只接受 2015-07-29 之前簽發的憑證，所以被 Code Integrity 拒絕。

## 2.2.2.0 套件

- 來源：SourceForge `com0com/2.2.2.0/com0com-2.2.2.0-x64-fre-signed.zip`，202,909 bytes，SHA-256 `3BC7313E8577774CE78CFF4D1C816FAF96CFA48C485BBCC5527D4569F7D5E373`
- `setup.exe`（NSIS）本身沒有簽章
- `com0com.cat` 簽章者 Steven William Hatchett，憑證 2010-09-22 簽發，經 GlobalSign ObjectSign CA → GlobalSign Primary Object Publishing CA → GlobalSign Root CA 交叉簽章到 Microsoft Code Verification Root，Certum 時間戳記
- `com0com.sys` 沒有內嵌簽章，由 catalog 涵蓋；版本 2.2.2.0，INF DriverVer 01/25/2011

## 步驟（一次 UAC）

1. 3.0.0.0 以 `uninstall.exe /S` 靜默移除，exit 0；之後 driver store 已沒有 3.x 套件，`com0com` 服務消失，再刪除殘留的安裝資料夾。
2. 2.2.2.0 以 `setup.exe /S` 靜默安裝，exit 0，安裝到 `C:\Program Files (x86)\com0com`；安裝本身不建立配對。
3. 建立兩組配對，同時開啟鮑率模擬與溢位模擬：
   - `setupc install PortName=COM10,EmuBR=yes,EmuOverrun=yes PortName=COM11,EmuBR=yes,EmuOverrun=yes`
   - `setupc install PortName=COM12,EmuBR=yes,EmuOverrun=yes PortName=COM13,EmuBR=yes,EmuOverrun=yes`
   - setupc 把四個號碼在 Windows 的 COM 號碼資料庫（ComDB）登記為使用中
4. 擁有權與 TX／Input／Output／RX 對應寫入 Simulator 目前的狀態資料夾（`owned.json`、`ports.txt`）。

## 結果

- 裝置：2 個匯流排、4 個埠全部 OK（`CM_PROB_NONE`）；`com0com` 服務 Running；COM 埠為 COM1、COM10–COM13
- Code Integrity：測試期間沒有新事件
- 雙向自測（.NET SerialPort，38400 8N1，無流量控制）：兩組配對、兩個方向都逐 byte 相符；單筆 27 bytes 從寫入到讀完需 12.9–24.3 ms
- 鮑率模擬：連續 100 筆分別花 678 ms、685 ms，理論值 703 ms
- [testing.md](../testing.md) 第二層：`posmv-simulator.exe --port COM10 --baud 38400 --rate 25 --count 100 --roll 1.29`，由 `posmv-sweep.exe --input-port COM11 --seconds 8 --rate 25 --off` 接收，收到 100 筆；`validate` 結果 valid=100、invalid=0、garbage_bytes=0

## 限制與風險

- 單筆延遲比 27 bytes 的線路時間（約 7 ms）長，推測是 Windows 計時器粒度（約 15.6 ms）造成，尚未查證。
- Microsoft 公告（2026-03-26，2026-06-09 更新）：從 2026 年 4 月的更新起，Windows 11 24H2、25H2、26H1 與 Server 2025 會逐步取消對交叉簽章核心驅動的信任。先進入評估模式（250 小時、3 次重開機）再強制，只有允許清單上的驅動例外。2.2.2.0 屬於交叉簽章，之後可能被擋。來源：<https://techcommunity.microsoft.com/blog/windows-itpro-blog/advancing-windows-driver-security-removing-trust-for-the-cross-signed-driver-pro/4504818>
- 2.2.2.0 的 `setupc.exe` 要求系統管理員權限，一般權限執行會失敗；它也不支援 `PortName=COM#` 自動配號。
- 配對資訊可在一般權限下從 `HKLM\SYSTEM\CurrentControlSet\Services\com0com\Parameters\CNCA<n>`／`CNCB<n>` 的 `PortName` 讀取。
- Simulator 目前的環境頁尚未支援 2.2.2.0：「下載並安裝」仍會下載 3.0.0.0，「建立」使用 2.2.2.0 不支援的 `COM#`，「檢查」與「自測」以一般權限呼叫 `setupc` 會失敗。
