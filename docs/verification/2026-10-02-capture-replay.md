# 實測：以提供的 POS MV capture 跑完整鏈（2026-10-02）

- 環境：同 [2026-10-02-virtual-com-lifecycle.md](2026-10-02-virtual-com-lifecycle.md)；COM10↔COM11、COM12↔COM13，com0com 2.2.2.0，38400 bps。
- 程式版本：本報告同一批 commit 的 Debug 建置。
- 操作方式：同 [2026-10-02-gui-end-to-end.md](2026-10-02-gui-end-to-end.md)。Capture 路徑以 Unicode 字元輸入，不經過輸入法，也不使用剪貼簿。

## Capture 內容

`tests/data/20260904_TSS1 POSMV.txt`：123,544 bytes，4577 行。

- 完整 Frame 4574 筆，狀態旗標全部是 G。
- 不完整的有三行：
  - 第一行從 Frame 中間開始。
  - 第 682 行多了一個字元：`:1211A61 -0269G 0433 -0328`。
  - 最後一行被截斷。
- 數值範圍：
  - Roll −16.02°～+18.74°
  - Pitch −17.63°～+16.88°
  - Heave −3.55～+0.12 m，從 −3.55 m 慢慢回到 0
- 前約 200 筆幾乎靜止（Roll −0.53°）。
- 錄製頻率：25 Hz（TSS1 沒有時間欄位，由使用者確認）。全長 183 秒，Roll 擺動的中位週期 3.1 秒。推論：比較像在台面上轉動 IMU，而不是船在海上的搖擺。

## 發現的問題：解析器拒收十六進位加速度（已修正，`b4d8423`）

- TSS1 開頭的 `XX`（水平加速度）與 `AAAA`（垂直加速度）是十六進位，例如 `:01001D`；但解析器只接受 0–9。
- 這份 capture 有 2605 筆含 A–F，佔完整 Frame 的 57%，全部被判為無效。
- 影響：修正前，正式程式在現場會丟掉這些 Frame，MBES 只會收到約 43% 的姿態資料，而且時間間隔不規則；Simulator 的預檢也只會顯示有效 1971 筆。
- 原因：自己產生的測試資料，加速度永遠是 `000000`，所以先前的測試都沒有抓到。
- 新增 CTest `capture`，直接用這份 capture 測：
  - 驗證器的統計：有效 4574、無效 2、垃圾 16 bytes。
  - Sweep OFF 時，轉送引擎逐 byte 原樣送出 4574 筆。
  - Sweep ON 時，每一筆只有 Roll 改變，而且差值等於 Offset。

  四項在舊版解析器下全部失敗，修正後全部通過。

## 判讀

- 修正後，真實 capture 的每一筆完整 Frame 都能通過正式程式：OFF 時逐 byte 相同，ON 時只改 Roll。這兩點也已納入 CTest。
- 真實 Roll 大幅擺動時，量到的 Offset 仍與設定一致，表示 Offset 沒有混入船體的 Roll。
- 這段 capture 的 Roll 本身就會超過 ±15° 的預設 MBES 上限，加上 Sweep 後更常超過，所以出現警告是預期的結果。
- 每次測試的前段都會出現一次較大的延遲（端到端 24–33 ms），p99 仍是 0.2 ms。原因還沒查明，留待 10 分鐘長測追蹤。
- 第 5 項開始前，為了改速率而停止送出超過 500 ms，正式程式因此判定輸入過期並關閉 Sweep，恢復後也維持關閉，符合設計（R1）。

## 這次新增的功能

- **Simulator 逐筆比對**：正式程式逐筆轉送（[ADR 0001](../adr/0001-forward-each-frame-on-arrival.md)），所以 RX 能以 Roll 以外的內容，把收到的 Frame 對回送出的那一筆。Capture 也適用；先前只能比對 Heave 有序號、由 Simulator 自己產生的資料。
  - 畫面顯示對上、相同、遺漏、對不上的筆數，以及延遲與量到的 Offset。
  - 送出 5 秒內沒有回來的 Frame 計為遺漏，所以循環播放時，內容相同的下一輪不會配錯。
- **COM 防呆**：
  - 正式程式開啟時，輸出預設的 COM 與輸入不同。
  - 兩者相同或沒有可用的埠時，「連線」停用，並顯示原因。
  - Simulator 的 TX 與 RX 相同時，不會開始測試。
